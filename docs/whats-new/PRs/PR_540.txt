title: feat(core): make business keys declarative over produced columns
description:
## Summary

keys now describe fields an entity produces instead of creating or reordering output columns; output
columns come only from producers (configured columns, loader-detected columns, extra_columns,
foreign keys, and unnest).

 - Core: TableConfig.get_columns() and related helpers no longer prepend keys; the fixed values
order becomes system_id, public_id, then data columns (build_fixed_entity_full_columns drops the
keys tier). A new BusinessKeyProducedValidator and MissingBusinessKeyError report keys the entity
does not produce at data-validation and runtime stages, and the structural keys_subset_of_columns
check now validates keys against all produced fields (columns, extra columns, FKs, unnest). SQL
auto-detect no longer requires keys to exist in the source query.
 - Backend: one authoritative fixed column order drives persistence, materialization, row-width
checks, and the values GET/PUT endpoints. Materialization no longer pads absent keys with null
columns and stores only data columns in columns. The values API accepts the authoritative order or
the recognized legacy key-inclusive order and rejects unknown, duplicate, or incomplete columns;
stored rows are presented in authoritative order without rewriting files.
 - Frontend: the entity editor hydrates from derived fixed-schema metadata, no longer auto-syncs
keys into columns, and persists produced data columns with identity fields left implicit.
 - Docs: glossary, user guide, and instruction files document that identity columns are permitted
(but discouraged) as keys and that keys never create columns. The DECLARATIVE_BUSINESS_KEYS proposal
and phase task plans are archived under docs/proposals/done/.

## User-facing release note

Business keys now only label fields an entity actually produces: you no longer need to duplicate
keys into columns, and if a key is not produced, validation and the UI report exactly which field is
missing and how to fix it. Fixed-entity tables no longer gain empty key columns.

## Upgrade notes

 - The authoritative fixed-entity column order changed from system_id → public_id → keys → data
columns to system_id → public_id → data columns. The values API still accepts the previous order for
recognized legacy requests and reorders rows by name, so existing saved files continue to work.
 - Entity configurations that list business keys the entity does not produce now fail structural
validation, fixed-schema checks, and data validation. Add the missing fields to columns or configure
the producer (extra_columns, foreign_keys, or unnest) that creates them. The PR author reports a
survey found no existing project configuring an unproduced business key.
 - Retiring the legacy fixed-values request-order path is deferred to a follow-up (#539); the 
compatibility path only accepts additional input shapes and is backward-compatible.
