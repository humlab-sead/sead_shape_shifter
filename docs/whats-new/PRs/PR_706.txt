title: Suppress reconciliation-pending status for valid direct-ID conditional
description:
## Summary

ConditionalForeignKeyConformanceValidator.validate_global in src/target_model/conformance.py now
skips the CONDITIONAL_FK_AWAITING_RECONCILIATION info issue when
is_valid_direct_public_id_foreign_key(...) confirms that a conditional foreign key is a valid direct
target-ID declaration. A valid direct-ID FK is already satisfied without a project lookup entity or
Core link, so reporting reconciliation as pending was misleading. The exemption is per foreign key:
local/default conditional FKs still await reconciliation, invalid direct-ID declarations keep their
errors (e.g. DIRECT_FK_TARGET_TABLE_MISSING), a second source using a different mode for the same
target keeps its own conditional status, globally required target entities remain required, and
DIRECT_FK_TARGET_CHECK_PENDING is unchanged.

The PR adds four conformance regression tests covering these cases and a PostgreSQL integration test
verifying that required_when still demands a direct-ID value on a selected insert and rejects
target IDs absent from the target table. Proposal and phase-plan documents are updated to record the
2026-11-11 approval and completed Phase 1 tasks, and scripts/README.md documents the loopback-only
disposable PostgreSQL container (spinup_disposable_postgres.py, make pg-disposable-*) used by the
integration test.

## User-facing release note

Conditional foreign keys that use an existing target ID directly are no longer reported as awaiting
reconciliation in project conformance, so valid declarations pass cleanly while genuinely unresolved
foreign keys and missing or invalid direct IDs are still flagged.

## Upgrade notes

None - no user action required.
