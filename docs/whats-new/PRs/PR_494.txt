## Summary

This PR establishes a three-directory deployment layout for target environments: ~/container
(replaceable code and build context), ~/config (environment configuration, credentials and policy,
mode 700), and ~/container-data (mutable runtime data and state). Deployment settings move out of
the checkout: the Makefile, scripts/load-env.sh, podman-compose.yml, the systemd unit, and all
lifecycle, backup, authorization, verification, and deploy scripts now resolve CONFIG_DIR (default
~/config) and DATA_DIR (default ~/container-data), with identical path-resolution rules in the
Makefile (resolve_path) and the shell loader. CONFIG_DIR/deployment.env replaces container/.env, and
CONFIG_DIR/backend.env plus CONFIG_DIR/.pgpass/.pgpass replace their container-data counterparts;
there is no fallback to the retired paths.

Key changes:

 - make setup creates ~/config and copies generic templates (deployment.env, backend.env, .pgpass)
without ever writing live configuration into the checkout, and reports missing operator-provisioned
authorization inputs.
 - The authorization bootstrap (bootstrap-authentication-and-authorization.sh) now reads
authorization.env, authorization-manifest.yaml, and groups.d/shape-shifter.conf only from CONFIG_DIR
— never from the repository secrets/ folder — and validates every input before touching htpasswd,
group files, roles, or the manifest. A new container/resources/authorization.env.example template
documents the inputs.
 - backup.sh archives mutable data at the archive root and runtime configuration (deployment.env,
backend.env, .pgpass) under config/ with modes preserved.
 - build.sh stages the UCanAccess dependency from container/lib/ucanaccess into the repository-root
build context when absent, so workdir and standalone builds use the same copy; install-ucanaccess.sh
replaces the installed copy only after a successful download. UCanAccess stays in the checkout as a
documented interim build-dependency exception.
 - rebuild-image.sh now requires --deploy-user (no test-user default) and its --dry-run reports
without acting; deploy helpers record settings in ~/config/deployment.env and never remove ~/config
or ~/container-data when refreshing the checkout.
 - Documentation (container/README.md, container/DEPLOYMENT.md including a new "Authorization
inputs" section, docs/OPERATIONS.md) describes the three-directory layout and marks the old paths as
retired. The cutover plan gains a Phase 2A section and a new
TARGET_ENVIRONMENT_CONFIGURATION_LAYOUT_TASK_PLAN.md recording the migration plan and validation
results.

## User-facing release note

Deployment configuration now lives in a ~/config directory next to the deployment checkout instead
of inside it, so operators edit ~/config/deployment.env and ~/config/backend.env, and the
~/container checkout can be replaced with a new release without touching configuration, credentials,
data, or the authorization database.

## Upgrade notes

Breaking change for existing deployments — there is no fallback to container/.env, secrets/.env, or
container-data/backend.env:

 - Migrate settings: copy container/.env to ~/config/deployment.env, and
~/container-data/backend.env and ~/container-data/.pgpass/.pgpass to ~/config/. Run make setup to
create ~/config (mode 700) and any missing templates; existing files are never overwritten.
 - Provision the authorization inputs by hand under ~/config before running the bootstrap:
authorization.env (from container/resources/authorization.env.example), authorization-manifest.yaml,
and groups.d/shape-shifter.conf. Deployment tooling does not copy policy or generate passwords.
 - rebuild-image.sh now requires --deploy-user; the previous test-user default is removed.
 - Direct podman-compose invocation is unsupported unless the operator explicitly exports CONFIG_DIR
and CONTAINER_DATA_DIR; use the Makefile or lifecycle scripts.
 - VITE_* build arguments and DEPLOY_ENVIRONMENTS are now read from ~/config/deployment.env.
