title: Implement direct target ID foreign keys
description:
## Summary

Adds an opt-in per-entity project declaration, foreign_key_value_sources, that lets a project tell
the SEAD change-request ingester that a target-model foreign-key column already holds an existing
target ID (public_id) instead of a local Core system_id link. The declaration applies only to the
change-request package: it never creates a Core FK link or dependency, and omitting it (or declaring
system_id) keeps the existing local-link behavior.

Key changes:

 - Project model and editor: TableConfig.foreign_key_value_sources (Core accessor, no
link/dependency side effects) and a typed Entity.foreign_key_value_sources field (literals
system_id/public_id) preserved through ProjectMapper; regenerated entitySchema.json and Monaco
coverage.
 - Validation and conformance: new ForeignKeyValueSourceSpecification rejects malformed maps and
non-empty maps without metadata.target_model (DIRECT_FK_VALUE_SOURCE_INVALID,
DIRECT_FK_TARGET_MODEL_REQUIRED); new ForeignKeyValueSourceConformanceValidator reports distinct
codes for unknown relationships, via FKs, missing public_id/target_table, Core-link conflicts, and
missing output columns; a non-overridable DirectForeignKeyPendingCheckValidator emits an
informational DIRECT_FK_TARGET_CHECK_PENDING. Valid direct declarations satisfy required-FK,
induced-entity, and no-orphan-facts checks while globally required target entities remain required.
validate_target_model now fails with DIRECT_FK_TARGET_MODEL_UNAVAILABLE when a direct map exists but
the target model cannot be resolved, instead of silently passing.
 - Ingester: input_resolution accepts and validates a standalone foreign_key_value_sources map in
IngesterConfig.extra; target projection, staging eligibility, package building, and inline-staging
SQL bypass local system_id mapping for declared direct FKs; the new direct_fk_validation.py checks
each packaged non-null direct ID through a read-only target lookup (integer column type plus row
existence) in both validate_tables() and ingest_tables(), failing closed when the ID is malformed,
absent, non-integer, or the lookup is unavailable. Supplied IDs never become KnownIdMapping/sidecar
entries, and used direct FKs are listed in the emitted manifest under direct_target_id_foreign_keys.
 - Saved-project flow: ProjectIngesterService derives the map from the resolved Core project and
passes it only to sead_change_request; direct-mode conformance errors stop validation/ingestion
before normalization, and strict route request fields keep callers from injecting the map.
 - Docs: new CONFIGURATION_GUIDE.md section and qualified AGENTS.md/src/AGENTS.md identity-tier
rules distinguish Core local-ID links from supplied target IDs; four phase-plan/task-plan documents
under docs/proposals/DIRECT_TARGET_ID_FOREIGN_KEYS/ record the design and execution.

## User-facing release note

Projects can now declare that a change-request foreign-key column already contains an existing SEAD
target ID (foreign_key_value_sources: <target>: public_id), so that relationship no longer needs a
helper project entity to translate local IDs. The ingester verifies every supplied ID against the
target database before accepting the package, and the package manifest records which foreign keys
used direct target IDs.

## Upgrade notes

No action is required for existing projects: an omitted or system_id declaration keeps the current
local-link behavior and package output. Projects that adopt public_id mode must resolve
metadata.target_model, output the target FK column, avoid a conflicting Core foreign_keys link to
the same target, and have the target database reachable, because the read-only ID lookup is
mandatory and validation/ingestion fail when it is unavailable. Change-request manifests may now
include a new direct_target_id_foreign_keys entry when a package uses direct IDs.
