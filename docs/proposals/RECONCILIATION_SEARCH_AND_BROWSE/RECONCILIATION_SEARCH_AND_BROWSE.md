## Summary

Add **Search** and **Browse** tabs to a persistent review pane beside the source-row queue. Search accepts the reviewer's own text and optional matching context, or `id: <positive integer>` for an exact, type-scoped lookup. Browse downloads the complete eligible list when it fits advertised row and response-byte limits, then filters and sorts it locally. If a list is too large, Browse reports that explicitly instead of showing a partial list as complete. Both modes select the same target-record identifiers; reviewers stage decisions in the browser and save them together.

Shape Shifter calls the Authority Service through its backend. Use OpenRefine reconciliation queries for ranked text search, optional entity suggestions for autocomplete, and an additive Authority Service API for bounded complete lists and optional record details. Shape Shifter does not query target database tables directly.

The proposal absorbs R16, R21, and R26–R30, plus the shared saved-row update in R2 and review entry in R24. It includes the minimum queue, navigation, notes, resume, and clear Save/Export distinction needed by this workspace. Recent-query history and derived application state remain deferred. See the [backlog disposition](./RECONCILIATION_SEARCH_AND_BROWSE_BACKLOG.md) for item-by-item scope and follow-ups.

## Problem

Candidate review is a poor starting point when most source rows describe new records. Reviewers need a quick way to check existing data, choose New when appropriate, and continue. Abbreviations and labels in another language also make the source label unsuitable as a search term: the reviewer may need to replace `Sthlm` with `Stockholm`, or supply an English term for a Swedish label. A reviewer who knows a target ID also needs an exact lookup that does not depend on searchable labels.

For classifiers, reviewers may recognize a value more easily than they can name it. A complete list of tens, hundreds, or a few thousand values can be useful when filtered and sorted interactively. A short ranked candidate list does not establish which values exist or whether the whole vocabulary has been searched.

Separate dialogs, mandatory prior matching, and entity-wide reloads make these activities slow. Direct database access would also create a second place to maintain target schema knowledge and identifier rules.

## Scope

- Shape Shifter: persistent pane, Search/Browse modes, source-row context, basic Needs review queue, keyboard operation, inline notes, explicit accept/New/skip actions, browser-side decision drafts, and one batch save.
- Backend support for resolving and validating source rows once per batch save and recording first-time decisions without batch matching.
- Authority Service: additive selection capabilities, interactive error reporting, per-type browse configuration, bounded complete lists, optional structured record details, and stable identifiers shared with reconciliation. Reuse the implemented manifest and per-query limit support; extend existing candidate verification to enabled types.
- Basic resume state, browser-side decision drafts, and clear **Save decision** versus **Export** actions. Show unsaved drafts; do not add recent-query history or calculate whether saved decisions are applied.
- Cross-service compatibility and end-to-end validation.
- Start with representative **`feature_type` and `country`** implementations. Gate search, browse, and export capabilities independently for each type; a type that has not passed its checks remains unadvertised without blocking another type. Add more types as needed. Both have supported reconciliation registrations on `dev`, but neither has export verification there. Live data availability and latency remain unverified.

## Non-Goals

- Automatic acceptance, automatic New decisions, automatic translation, or learning aliases from operator queries.
- Creating target records, allocating IDs, or making SIMS calls while searching, browsing, or recording a review decision.
- Redesigning explicit export, offline normalization, manual-link precedence, or Core foreign-key identity semantics. This proposal adds a verification gate for accepted candidate links before export.
- Bulk assignment/actions beyond saving individually chosen drafts together, batch matching progress/caching, complete audit history, undo, or rollback of exported links.
- Measuring improvement against the current workflow. It has never been used in production and is not a suitable baseline; measurements of the new workflow establish the baseline for future improvements.
- Universal database exploration, arbitrary SQL/columns/joins, advanced wildcard syntax, or a mandatory taxonomy tree browser.
- A Saved decisions view in the Search/Browse workspace. Saved decisions remain available through the existing legacy review grid; adding in-workspace inspection is deferred to [backlog item R34](../RECONCILIATION_IMPROVEMENTS_BACKLOG.md#r34-inspect-saved-decisions-in-the-searchbrowse-workspace).
- Redesigning all reconciliation configuration or implementing the whole improvement backlog.

## Proposed Design

### 1. One pane, two ways to find a record

The left queue retains the source label, business key, and review state. The right pane stays open while the active source row changes. It shows read-only source context, a **Search / Browse** switch, target results, optional notes, and persistent decision controls.

| Action | Behaviour |
|---|---|
| Search | Type an expansion, translated term, or name for ranked search, or enter `id: 42` for an exact lookup by target ID. The source label is offered as a convenience, not forced into the query. Enter submits immediately; optional typeahead is debounced. |
| Browse | Download the complete type-specific list when it is within the advertised row and response-byte limits. Narrow and sort the returned rows locally; inspect definitions when available. A browse filter is independent of the ranked search query. An oversized list produces an explicit “too large to browse” result, never a partial list presented as complete. |
| Draft selected & next | Stage an accepted decision for the active business key and selected target URI in the browser; advance after the draft is recorded. |
| Draft New & next | Stage a New/local-only decision. Explain that this approves later new-record handling, not immediate creation. Search is optional. |
| Save decisions | Submit all staged decisions as one batch. The backend resolves and validates current source rows once, then conditionally writes the whole batch. Clear drafts only after success. |
| Skip for now | Advance without adding a decision; retain the row in Needs review and offer return to deferred rows. Preserve any draft already staged for that row. |

An empty result never marks New. Search failure, no results, loading, and not-yet-searched are distinct states. Opening a new workspace requires an Authority Service response for capability discovery; cold-start offline capability discovery is not supported. After a workspace has opened, reviewers can stage and save a New-only batch during an Authority Service outage; source rows are still resolved and validated at save time. Inspecting saved decisions from within this workspace is deferred to R34; use the existing legacy review grid for that task.

Switching tabs preserves the active source row and each tab's filters, but clears the selected target unless the same record remains present in the current results. On another source row, clear target selection and old responses; show only that row's own query, note, and decision drafts. Retain unsaved work per row or warn before discarding it. Browse filters and sort may persist for the specification. No result is pre-accepted or automatically carried to another row.

Use ordinary keyboard navigation within results. Enter in the text field searches; explicit modified shortcuts stage decisions. Bare-letter grid shortcuts are inactive during text entry, including composition input. Staging advances through the visible queue; it does not mark a decision as saved. A successful batch save confirms all included drafts. A failed save leaves the catalog unchanged and preserves every draft.

### 2. Responsibility and protocol

| Component | Owns |
|---|---|
| Shape Shifter frontend | Source queue, focus, request state, result selection, keyboard operation, and browser-side draft/resume state. |
| Shape Shifter backend | Project authorization, current source-row resolution and validation at batch save, Authority calls, record adaptation, conditional batch writes, and export status. |
| Authority Service | Served target-record set, per-type lookup/list/details, supported filters and sorts, target identifiers, capability metadata, and target database access. |
| SIMS | Its existing downstream identity responsibilities. This workspace makes no resolve, bind, or allocation calls. |

Ordinary Search text uses a single-query OpenRefine `POST /reconcile` request with operator text, configured type, supported property hints, and an effective result limit. The explicit `id: <positive integer>` syntax, such as `id: 42`, instead performs an exact target-ID lookup for the configured type; it does not call fuzzy reconciliation. If a query starts with `id:` but does not contain a valid positive decimal integer, show an input error and do not fall back to fuzzy search. A numeric query without the `id:` prefix remains ordinary search text. Advertise exact ID lookup per type; an unsupported lookup returns an explicit unsupported result. Entity suggest is optional for autocomplete, never a required extra request before submitting a search. Keep the type fixed to the specification. Clearly distinguish supported property hints used for ranking from browse filters that strictly restrict results. The current configured classifiers declare no reconciliation properties; do not offer context controls for them unless service support is added. Resolve advertised property IDs through the existing manifest validation.

Only advertise interactive search for bounded, read-only retrieval that meets the agreed response budget. Do not run LLM/RAG reasoning on each keystroke. Types whose existing strategy is too expensive remain unsupported for interactive search until a suitable lookup is supplied; batch matching behaviour stays unchanged.

Browsing and optional structured details use a versioned additive Authority API. They are not represented as empty fuzzy searches. The OpenRefine 0.2 [suggest contract](https://www.w3.org/community/reports/reconciliation/CG-FINAL-specs-0.2-20230410/#suggest-queries) provides a cursor for suggestions, but does not define this proposal's exhaustive listing or browse-filter semantics.

All retrieval is read-only. It neither writes proposals for every result nor changes the mapping sidecar. Browsed records have no invented confidence or `match=true` flag; a reviewer decision is required regardless of how the record was found.

### 3. Capabilities and record-list contract

The Authority Service owns the following **proposed** extension contract, version 1. Paths are recommendations for this proposal, not descriptions of existing routes.

| Interface | Contract |
|---|---|
| `GET /reconcile` | Preserve standard fields and the implemented, explicitly serialized `reconciliation.supportedTypes` extension. Add optional `reconciliation.record_selection` metadata with `version: 1` and a same-service relative `types_path`. |
| `GET /records/types` | Return per-type `search_supported`, `identifier_search_supported`, and `browse_supported`, display columns, local text/filter/sort fields, row and response-byte limits, and type-specific URI/ID metadata sufficient for local URI/ID validation, including whether existing candidate verification supports the type. Keep text search, exact ID lookup, browsing, and export-verification support distinct. Absence of a capability means unsupported. |
| `GET /records/{type}` | Return the complete projected list for the type only when it fits the advertised row and response-byte limits. Do not accept filter, sort, or paging parameters. If either limit would be exceeded, return an explicit `too_large_to_browse` error with no partial items. |
| `GET /records/{type}/details` | Accept exactly one of `id` (the complete target URI) or `target_id` (a positive integer). The `target_id` lookup is restricted to `{type}` and returns that exact record. Return a structured record or an explicit not-found/invalid-ID outcome. The `target_id` form serves `id: <positive integer>` Search queries. Do not require a details request to save a decision, and do not return executable HTML as the structured details contract. |

Search, browse, and details resolve to the same target-record set and IDs. A record contains `id` (the complete reconciliation URI), `target_id` (the positive numeric target ID supported by the current decision model), `type`, `name`, optional `description`, and declared display `fields`. Browse results include the fields needed to identify and display a choice; details are fetched only when additional information is needed. Names are not identifiers. A shared Authority formatter/parser supplies these values; the Vue pane does not introduce another URI parser. Shape Shifter uses one type-aware local validator for all decision writes and export preflight. It uses trusted type-specific identifier metadata to parse the exact URI format, checks that the URI's type matches the saved type, requires a positive `target_id`, and requires the ID parsed from the URI to equal `target_id`. It does not infer a type from trailing digits. New decisions do not require a target reference. These checks validate the saved decision's shape, not whether the target still exists. Do not call details or candidate verification as a prerequisite to saving an accepted decision. The existing candidate-verification protocol checks target existence at export and must succeed before an accepted candidate link is written.

The exact-ID lookup is the response to the reviewer's explicit identity query, not a second validation request when accepting a result. A result selected from ordinary text search or Browse does not need another details request before it can be saved.

Successful list responses contain `items` and `completeness: "complete"`. Do not include paging cursors or filtered totals. The client can count the complete list and its locally filtered results. Search results remain labelled limited/ranked suggestions, with no claim that a search miss proves absence.

Browse text filters use case-insensitive literal substring matching over advertised fields; declared field filters combine using AND. `%`, `_`, `*`, and similar characters are literal input, not implicit SQL or wildcard syntax. Labels, descriptions, and codes are searchable only where actually provided; aliases are searchable only if supplied and advertised. Sort the complete returned list locally, with label ascending and numeric target ID as a unique tie-breaker by default. Define null placement and collation consistently in the client.

The first release returns a complete list or an explicit too-large result; it never returns a partial list as complete. Apply row and serialized-response-byte limits per type. Local filtering and sorting operate only on a complete response. Lists reflect the target data when fetched, not a transaction snapshot; reviewers can refresh before saving or exporting. Add server paging only if measured type sizes or response times show that the bounded complete-list approach is insufficient.

### 4. Authority Service implementation responsibilities

Add bounded-list and optional details capabilities to the existing registered type and repository system. Browse support is opt-in per type; being present in `config/entities.yml` or having a fuzzy strategy does not by itself make a type browsable. A type declares its list source, projected fields, locally usable filters/sorts, optional details lookup, and row/byte limits in service-owned configuration. Use existing connection/configuration facilities and generated schema conventions. Build configured-classifier projections from the existing `table_specs` and generated views; retain their static registry and startup validation. Do not introduce a parallel classifier registry or hand-edit generated SQL. Use a separate adapter for non-classifier types such as `country`.

Only declared identifiers are used in SQL construction; values are parameterized. List, details, search, and export verification must agree about the exposed record set. The new API exposes intended record fields, not arbitrary underlying tables. Unsupported types return a capability error; database timeouts/unavailability return failures, not empty lists. Expose swallowed suggestion/details errors on the interactive path. Preserve implemented per-query reconciliation limits and default fallback; enforce the declared interactive cap without changing legacy queries. Autocomplete may keep a bounded fixed limit if advertised. Do not relabel the existing classifier prefix lookup as substring search.

For the representative `feature_type` and `country` types, provide a complete browse projection with at least ID and label, plus description where available. `feature_type` reuses its configured classifier view and `feature_type_id`; `country` uses the country subset of location records, `location_id`, and the existing `/country/{location_id}` URI shape. Enforce country membership in list, optional structured details, and verification, including a negative fixture for a non-country location ID. Advertise each type's browse and export-verification capabilities only after that type passes its checks.

Extend `POST /reconcile/verify-candidates` for each type before advertising that type's export capability, using the same read-only, type-specific existence checks as list/details. Preserve ordered batches, echoed type/URI, existing outcomes, and the positive numeric result field `aggregate_id` expected by Shape Shifter. For these lookups that field carries the target primary key; its legacy name does not require a SIMS aggregate or binding operation. Verification must not depend on SIMS `bind_existing` policy. A type that is not export-ready does not block another type whose checks pass.

Before export, apply the shared local validator to every accepted catalog decision the export would write. If any entry is invalid, report its row-specific validation issue and block the export before changing the sidecar. For locally valid entries, verify every accepted candidate link, including links already saved in the catalog. Keep the existing verification protocol, but require success before writing accepted links to the sidecar. `unsupported_type`, malformed replies, wrong-type IDs, and Authority/database unavailability block that export; never fall back to writing an unverified accepted link. An export with no accepted candidate links, such as one containing only valid New decisions, may proceed during an outage. This deliberately replaces the current outage fallback without replacing the export protocol. Preserve the existing site verification query and response contract, and apply the export gate to its failures too. Do not advertise a type as export-ready based solely on `supportedTypes` or a successful list request. Extend `/reconcile/readiness` only if the new capability contract uses it for export readiness; its current site-only coverage is not a universal matching prerequisite.

This proposal does not choose how later exports should handle accepted links that earlier versions already wrote without verification. Do not silently repair or remove those sidecar entries under this proposal.

Test complete lists below each type's row and byte limits, plus explicit too-large outcomes when either limit is exceeded. Do not claim that production classifiers contain thousands of values without measuring them. Other strategies, especially external or LLM-backed ones, can continue to offer their existing batch behaviour without browse support.

### 5. First-time decisions and batched saves in Shape Shifter

Keep each chosen decision as a browser draft scoped to project, specification, entity, field, and business key. Include the source-row identity and displayed values needed to detect a changed row. Drafts are not catalog decisions. Do not create server-owned review snapshots, opaque row tokens, server-side session storage, session expiration, or source-revision providers.

Add a batch decision operation that accepts each staged business key, its source-row identity and displayed values, accepted/New status, target URI/ID when accepted, and optional notes. Resolve the current authorized source rows once per batch save, using the established source-resolution rules, including another-entity or SQL search sources. Validate every drafted key against the resolved rows; reject missing, duplicate, unauthorized, or changed rows, and do not trust client-supplied labels or values as source data. Validate accepted target references with the shared local validator, but do not perform a details or existence lookup when saving the decision.

Resolve and validate before taking the project lock. Then, under the project lock, load the catalog and apply every valid decision as a per-key change, so a concurrent write to other business keys survives. If any draft is invalid, reject the whole batch without writing any decisions. Return the saved decisions on success. Use the same local validator for legacy decision routes and whole-catalog JSON/YAML replacement, and take the project lock for every catalog write, including the registry create and update routes. Validate every accepted reference in a replacement before writing any part of it; if any entry is invalid, reject the replacement atomically and return all row-specific validation issues. When loading an existing catalog, keep invalid entries visible with their validation issues instead of dropping or silently changing them. Let reviewers repair an invalid entry through the decision flow or correct the catalog and resubmit it. Valid prior manual reconciliations remain reusable and do not need to be entered again. Do not add per-row version storage. Preserve project authorization and export verification. Do not weaken checks for browsed selections.

Source changes that alter a drafted row's key or displayed values are detected by the save-time resolution and validation. Unversioned external SQL data is checked as observed during that resolution; changes after it are not detectable without another save attempt. Preserve all drafts after a failed batch and let the reviewer refresh or correct them before retrying. R22's broader reassessment of historical decisions remains separate.

A batch may include New decisions without prior matching or an Authority call for those entries. Invalid or duplicate keys cannot be saved as New. Marking New never clears a conflicting existing public ID or protected manual link silently; use the established export/ingester conflict rules and show the resulting block.

On success, patch the affected rows and queue counts from the response and clear the saved drafts. Do not reload the full preview or resolve source rows once per decision. On failure, leave the catalog unchanged and preserve all drafts. Legacy decision routes remain supported and share validation; callers need not supply browser draft state and keep their current payloads. Detecting a stale view belongs to the workspace: when a save would replace content that changed since the reviewer loaded it, warn first and keep the staged drafts so the reviewer can reapply them.

Catalog decisions still require explicit export. Label the actions and outcomes clearly: **Save decision** stores the review decision in the catalog; **Export** applies saved decisions to the mapping sidecar. Do not add a derived per-specification application-state calculation in this release. Keep existing current-ID provenance, verification indicators, and export outcomes.

### 6. Request state, persistence, and compatibility

- Debounce typeahead initially at 300 ms; Enter submits immediately and cancels the scheduled duplicate. Ignore unfinished composition input. A type may require explicit submit if it does not advertise interactive lookup.
- Cancel superseded requests where possible and always ignore responses whose project/specification, row, mode, query, or context no longer matches. Clear obsolete target selection immediately. Failed search/browse/details requests remain distinguishable from successful empty results.
- Retain active specification, mode, focused source key, tab-specific filter/sort, and per-row query and decision drafts in versioned browser storage. Show decision drafts as unsaved until a batch succeeds. Never persist full target collections as if fresh, or restore an old result as a confirmed selection. Recent-query history is deferred.
- Load optional capabilities independently of legacy manifest parsing, but require an Authority Service response when opening a new workspace; do not support cold-start offline capability discovery. A missing browse extension hides Browse and leaves existing search/candidate review usable. Invalid extension metadata disables the affected extension with an explanation. If Authority becomes unavailable after the workspace opens, inspection of saved decisions and locally valid New decisions remains available.
- Model new metadata explicitly in the Authority response DTO and the Shape Shifter adapter. Test actual manifest HTTP output, including required existing extensions, rather than only a metadata-builder dictionary. Service paths must resolve within the configured Authority service, never to caller-selected hosts.
- Keep old reconciliation routes and catalogs readable. Legacy whole-catalog replacement and decision routes remain available, and every catalog write takes the project lock, so a stale view cannot discard another writer's changes to other rows. Browsing configuration lives in the Authority Service; projects do not acquire database table/column settings. Draft UI state is not a new catalog status or authorization to allocate.

## Alternatives Considered

| Alternative | Assessment |
|---|---|
| Query SEAD directly from Shape Shifter | Rejected: duplicates target schema, access, and identifier knowledge in the editor backend. |
| Make every interaction a fuzzy reconciliation query | Rejected for browsing: ranked top-N results cannot promise complete enumeration or global sorting. |
| Use only an extended suggestion endpoint | Useful for autocomplete, but a dedicated list contract can distinguish a complete bounded list from an oversized list without overloading ranked search. |
| Fetch every classifier in full immediately | Do not enable this for every registered type. Start with representative types and per-type row/byte limits; return an explicit too-large result when needed. Add server paging only if measurements show the bounded complete-list approach is insufficient. |
| Require batch matching before every review | Rejected: it preserves the main bottleneck for mostly-new rows and unsuitable source labels. |
| Replace catalogs/export or write trusted manual links | Rejected: record selection should preserve existing human decisions, ownership, and export semantics. |

## Risks And Tradeoffs

- **Paired deployment and type coverage:** `dev` contains the required manifest and verification routes, but verification currently covers only `site`. Extend verification and test the exact deployed pair before advertising export support for each type; a saved decision does not prove target existence.
- **Live target data:** A complete list reflects target data when fetched, not a snapshot across later edits. Refresh when needed; export verification remains authoritative before accepted links are written.
- **Draft durability and source freshness:** Decisions remain browser drafts until one batch save succeeds, so cleared browser storage can lose unsaved work. Show the unsaved count and preserve drafts after failure. The batch resolves current source rows once; changes to unversioned external data after that resolution are not detectable. If immediate per-row durability later proves necessary, measure before adding a server-side session lifecycle.
- **Catalog write conflicts:** Writes are serialized per project, so two reviewers save in turn and neither loses the other's changes to other rows. A save that targets the same business key wins on a last-writer-wins basis. The workspace warns the reviewer before a save replaces content that changed since it was loaded, which avoids per-row version storage.
- **Response time:** Some matching strategies can be expensive. Advertise interactive support only where bounded lookup is available, and measure the pilot before setting a latency promise.
- **List size:** Some types may exceed the advertised row or response-byte limits. Report those types as too large to browse rather than returning a partial list; measure before adding paging.
- **Accidental New decisions:** Fast actions increase speed and mistakes. Use explicit labels and focus-scoped shortcuts, preserve failed work, and keep New distinct from a search miss. Undo remains separate work.

## Acceptance Criteria

- **P-AC-1 — Entry and source identity:** Review opens without Find Candidates. Search text, browse filters, and selected target IDs never change source labels, ordered business keys, or Core `system_id` values.
- **P-AC-2 — Continuous review:** Ten consecutive rows can be searched/browsed, decisions staged or skipped, and advanced in one pane using keyboard or labelled controls. The staged decisions save together; a failed batch leaves every draft intact and does not mark any decision as saved.
- **P-AC-3 — Search:** Expanded abbreviations and operator-translated labels find expected pilot records through the Authority API; declared context is applied with its advertised semantics; requested bounded result limits are honored. `id: <positive integer>` returns the exact record for the configured type even when its label does not contain the ID. Unknown IDs return no record, and malformed `id:` syntax returns an input error without fuzzy fallback.
- **P-AC-4 — Complete browse:** Each advertised browse type returns either a complete list within its row and response-byte limits or an explicit too-large result with no partial items. Declared text/field filters and sorting operate locally over the complete list; no paging or exact server-side filtered totals are required.
- **P-AC-5 — Uniform targets:** Search, Browse, optional details, and export identify the same records. A browsed choice has the same URI and numeric target ID as an equivalent searched choice and can be saved without a details lookup; browse rows do not invent confidence scores. The shared local validator enforces the type-specific URI format, saved type, positive `target_id`, and URI/ID agreement on every accepted-decision path. Export verifies accepted links using the existing protocol before writing them. Each type advertised as export-ready passes verification with ordered echoed IDs and matching numeric `aggregate_id`. Wrong types and non-country location IDs cannot become exported country links; existing site checks still pass.
- **P-AC-6 — First-time saves:** A valid keyed row with no catalog entry can be accepted or marked New without prior matching. At batch save, missing, duplicate, unauthorized, or changed source rows reject the whole batch without catalog changes. Every decision and whole-catalog writer loads, changes, and saves under the project lock, so no writer can overwrite another writer's changes to other rows. Whole-catalog replacements validate every accepted reference atomically and report all invalid entries without writing. Existing invalid entries remain visible with repairable validation issues; valid prior manual reconciliations remain reusable.
- **P-AC-7 — Explicit decisions:** Retrieval creates no catalog decision, sidecar change, target record, or SIMS state. Empty results and failed requests never approve New. After a workspace has opened, a batch containing only valid New decisions can be saved during a remote-service outage and still requires export before becoming an allocation approval. An export containing only valid New decisions remains available during an outage.
- **P-AC-8 — Batched saved-row updates:** A batch resolves and validates source rows once, regardless of the number of drafts. Success updates only affected review state and returns the saved decisions; failures make no partial catalog changes and preserve all drafts. Changed source rows require review before retry. A reviewer whose view changed since it was loaded is warned before a save replaces newer content, and their staged drafts survive that warning.
- **P-AC-9 — Request correctness:** Stale/out-of-order responses cannot appear as current results or enable acceptance. Searching, empty, failed, unsupported, and invalid `id:` input states are distinguishable; literal filter input cannot introduce SQL or wildcard semantics.
- **P-AC-10 — Capability and compatibility:** Actual HTTP manifests expose supported types and versioned selection capabilities without breaking standard OpenRefine fields. Opening a new workspace requires an Authority Service response; cold-start offline capability discovery is not supported. Missing/unsupported Browse leaves legacy review available; unadvertised types/filters/sorts are not used. Text search, exact ID lookup, Browse, and export-verification support are advertised independently per type. A saved decision does not prove target existence; unsupported verification or verification failure blocks export of accepted candidate links, and service outages never permit them to be exported unverified.
- **P-AC-11 — Resume:** The workspace restores scoped mode/filter/sort/focused key, per-row query drafts, and decision drafts from browser storage. Restored decisions remain visibly unsaved and scoped to their original project/specification/entity/business key. Recent-query history is not stored. Another row or project never inherits a draft or a confirmed target selection.
- **P-AC-12 — Export invariants:** Saved accepted and New decisions are not applied until explicit export. The UI clearly distinguishes **Save decision** from **Export** and does not calculate a derived application state. Export locally validates every accepted reference before making sidecar changes, then writes links only after Authority verification succeeds; an invalid entry or outage blocks an export containing accepted links, with no unverified fallback. Manual/unowned link protection, ownership cleanup, offline normalization, and downstream FK semantics remain unchanged.
- **P-AC-13 — Pilot validation:** Each advertised type passes its own paired integration and keyboard/browser checks, with timing and request-count results recorded as the new workflow's initial baseline in a named environment and no retrieval-time writes. No comparison with the current workflow is required. A type that has not passed remains unadvertised; its failure does not block a different type that has passed.
